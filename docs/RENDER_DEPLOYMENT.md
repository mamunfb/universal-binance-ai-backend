# Render deployment guide (temporary onrender.com hostname)

This project can be tested on Render without buying a domain. Render assigns a service hostname under `onrender.com`.

## Blueprint configuration

The repository root contains `render.yaml`. It defines one Docker-based web service:

- Service: `universal-binance-ai-backend`
- Region: Singapore
- Plan: Free (testing only)
- Source branch: `fix/binance-public-market-data-endpoints`
- Dockerfile: `./Dockerfile`
- Health check: `/health`
- Automatic deploys: disabled; deploy manually after reviewing CI
- `PERSONAL_API_KEY`: generated by Render
- `DATABASE_URL`: entered privately in Render during Blueprint setup/sync
- `REQUIRE_DATABASE_URL=true`: prevents production startup unless the Neon connection string is configured; this avoids silently falling back to ephemeral SQLite storage
- `COLLECTOR_SHUTDOWN_TIMEOUT_SECONDS`: optional graceful-shutdown timeout per collector (default 15 seconds; valid range greater than 0 and at most 300 seconds)

Do not change the source branch to `main` until the owner explicitly approves merging and deployment.

## Background collector deployment safety

The five optional background collectors are disabled by default. If any collector is enabled, run only one collector-owning application process for each configured job set and database. Do not scale the collector-enabled web service to multiple instances: each instance starts its own process-local collector tasks and may duplicate Binance stream connections, REST polling, database writes, and upstream quota use. The current application does not implement a distributed lease or leader election. Keep all collector enable flags disabled on a horizontally scaled web service until a separately coordinated worker/lease design is implemented and tested.

Collector status is process-local; a status response from one web instance does not report the state of other instances. The current Render Blueprint declares one Free web service, but this is not proof of the live service's instance count or environment configuration.

## Create the Render service

1. Sign in to Render and choose **New → Blueprint**.
2. Connect the GitHub repository `mamunfb/universal-binance-ai-backend`.
3. Select branch `fix/binance-public-market-data-endpoints` (not `main`).
4. Let Render read the root `render.yaml` and review the proposed service before syncing.
5. When prompted for `DATABASE_URL`, paste the pooled PostgreSQL connection string from the intended Neon branch into Render's secret field. This value is required: the service intentionally fails startup without it. Never put it in GitHub, source code, screenshots, or chat.
6. Confirm the service is on the Free plan and Singapore region, then create/sync the Blueprint.
7. Trigger the first deploy manually. Automatic deploys are intentionally disabled.

Render assigns the actual `onrender.com` hostname after the service is created. Do not assume the hostname until Render displays it.

## Post-deploy acceptance checks

After the deploy completes, use the exact hostname shown by Render:

- `GET /health` must return HTTP 200 and `{"status":"ok",...}`.
- Open `/dashboard` and confirm the page loads.
- Open `/docs` to inspect the API schema.
- Confirm a protected `/api/*` request without a Bearer key is rejected.
- Confirm a request with the generated `PERSONAL_API_KEY` succeeds.
- Verify PostgreSQL-backed insert/read and persistence after a service restart before accepting the deployment.

Do not mark deployment complete based only on a successful container build or health check.

## Free-plan limitations

Render Free web services spin down after 15 minutes without inbound traffic and may take about a minute to wake. Their local filesystem is ephemeral: SQLite files are not durable across spin-down, restart, or redeploy. The Neon `DATABASE_URL` is mandatory for this Render service: `REQUIRE_DATABASE_URL=true` makes startup fail if it is missing. It must be configured and verified before using historical collection or dashboard persistence. Free instances are for testing/hobby use, not production workloads; review current Render plan limits before launch.

## Security

- Keep `PERSONAL_API_KEY` and `DATABASE_URL` only in Render's environment/secret settings.
- Do not commit `.env` or paste secrets into issues, pull requests, or chat.
- Keep auto-deploy disabled until CI is green and a manual deployment is explicitly approved.
- Do not merge PR #21 or deploy to production without the owner's explicit approval.

## Cloudflare custom domain (optional; configure only after Render service exists)

Use this sequence when the owner supplies a registered domain and the Render service has an actual `onrender.com` hostname. Do not guess the hostname or modify registrar nameservers/DNS records before reviewing the existing DNS zone.

1. Add the custom domain to the Render service in the Render Dashboard and copy the exact `onrender.com` target shown by Render.
2. In Cloudflare, open **SSL/TLS → Overview** and set the encryption mode to **Full**, following Render's Cloudflare-specific instructions.
3. In **DNS → Records**, create the required CNAME record(s), such as `@` for the apex and `www` for the www hostname, targeting the exact Render `onrender.com` hostname.
4. Keep those CNAME records **DNS only** while Render verifies the domain and issues its certificate. Remove conflicting `AAAA` records for the hostname because Render's current Cloudflare guide says IPv6 AAAA records can interfere with custom-domain behavior.
5. Wait until the Render Dashboard reports that the custom domain is verified and its certificate is issued/valid. Only then may the owner optionally switch the web CNAME records to **Proxied** in Cloudflare.
6. Re-test HTTPS, redirects, `/health`, `/dashboard`, authenticated API access, and PostgreSQL persistence through the custom hostname before treating the setup as accepted.

Do not proxy mail, verification, or unrelated DNS records as part of this change. Preserve existing MX, TXT, SPF, DKIM, and DMARC records. Cloudflare proxying is an optional later step; DNS setup alone does not deploy the application or secure an API whose application authentication is misconfigured.

Official provider instructions: [Render — Configuring Cloudflare DNS](https://render.com/docs/configure-cloudflare-dns). The record target, domain ownership, current DNS zone, and certificate state must be read from the owner's actual accounts; this repository does not contain those values.
## Reverse-proxy and browser security notes

The current FastAPI application does not install proxy-header middleware, a trusted-host middleware, HTTPS redirect middleware, or CORS middleware. Its browser security headers include `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Permissions-Policy`; it does not currently emit HSTS. The dashboard calls the API on the configured backend origin, so a same-origin deployment does not require permissive CORS rules.

For the Cloudflare custom-domain rollout:

- Keep TLS termination at Cloudflare/Render as documented by Render. Do not add blanket trust for arbitrary `X-Forwarded-*` headers; the application currently does not need those headers to construct redirects.
- Do not add application-level HTTPS redirects or trust client-supplied forwarded-proto headers without a narrowly configured trusted-proxy boundary and tests.
- Configure HSTS at the trusted edge only after the custom hostname has a valid HTTPS certificate and all intended subdomains are confirmed HTTPS-capable. Start without `includeSubDomains` or preload unless the owner has verified those broader requirements.
- Do not add `Access-Control-Allow-Origin: *` as a Cloudflare workaround. If the dashboard and API are kept on the same origin, no cross-origin browser access is required.
- Keep the private API Bearer key out of URLs, DNS records, Cloudflare rules, and browser persistent storage. The current dashboard asks for the key in a password input and does not persist it.

These are deployment safeguards, not evidence that Cloudflare is already connected or that the live Render service has been inspected.
