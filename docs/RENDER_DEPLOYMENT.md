# Render deployment guide (temporary onrender.com hostname)

This project can be tested on Render without buying a domain. Render assigns a service hostname under `onrender.com`.

## Blueprint configuration

The repository root contains `render.yaml`. It defines one Docker-based web service:

- Service: `universal-binance-ai-backend`
- Region: Singapore
- Plan: Free (testing only)
- Source branch: `fix/binance-public-market-data-endpoints`
- Dockerfile: `./Dockerfile`
- Health check: `/health`
- Automatic deploys: disabled; deploy manually after reviewing CI
- `PERSONAL_API_KEY`: generated by Render
- `DATABASE_URL`: entered privately in Render during Blueprint setup/sync
- `REQUIRE_DATABASE_URL=true`: prevents production startup unless the Neon connection string is configured; this avoids silently falling back to ephemeral SQLite storage

Do not change the source branch to `main` until the owner explicitly approves merging and deployment.

## Create the Render service

1. Sign in to Render and choose **New → Blueprint**.
2. Connect the GitHub repository `mamunfb/universal-binance-ai-backend`.
3. Select branch `fix/binance-public-market-data-endpoints` (not `main`).
4. Let Render read the root `render.yaml` and review the proposed service before syncing.
5. When prompted for `DATABASE_URL`, paste the pooled PostgreSQL connection string from the intended Neon branch into Render's secret field. This value is required: the service intentionally fails startup without it. Never put it in GitHub, source code, screenshots, or chat.
6. Confirm the service is on the Free plan and Singapore region, then create/sync the Blueprint.
7. Trigger the first deploy manually. Automatic deploys are intentionally disabled.

Render assigns the actual `onrender.com` hostname after the service is created. Do not assume the hostname until Render displays it.

## Post-deploy acceptance checks

After the deploy completes, use the exact hostname shown by Render:

- `GET /health` must return HTTP 200 and `{"status":"ok",...}`.
- Open `/dashboard` and confirm the page loads.
- Open `/docs` to inspect the API schema.
- Confirm a protected `/api/*` request without a Bearer key is rejected.
- Confirm a request with the generated `PERSONAL_API_KEY` succeeds.
- Verify PostgreSQL-backed insert/read and persistence after a service restart before accepting the deployment.

Do not mark deployment complete based only on a successful container build or health check.

## Free-plan limitations

Render Free web services spin down after 15 minutes without inbound traffic and may take about a minute to wake. Their local filesystem is ephemeral: SQLite files are not durable across spin-down, restart, or redeploy. The Neon `DATABASE_URL` is mandatory for this Render service: `REQUIRE_DATABASE_URL=true` makes startup fail if it is missing. It must be configured and verified before using historical collection or dashboard persistence. Free instances are for testing/hobby use, not production workloads; review current Render plan limits before launch.

## Distributed background collector ownership

Before enabling any background collector on a PostgreSQL deployment, apply all migrations in order, including `migrations/011_collector_leases.sql` and `migrations/012_collector_lease_fencing_generation.sql`, to the primary `DATABASE_URL`. The application does not run schema migrations automatically.

All application instances that share collector data must use the same primary `DATABASE_URL`. Each collector group claims one PostgreSQL lease row before starting:
- Liquidation stream: `liquidation:all`
- Order-book streams: `order-book:all`
- Aggregate-trade streams: `aggregate-trades:all`
- Funding/open-interest history: `derivatives-history:all`
- Historical Klines: `historical-klines:all`

The coordinator uses PostgreSQL server time, a 30-second lease, a 10-second renewal heartbeat, and a 5-second retry interval. A process that cannot acquire a lease waits without starting that collector. Graceful shutdown stops the collector and releases its lease; after an abrupt process loss, another instance can take ownership after the lease expires. If lease acquisition or renewal fails, the coordinator fails closed and stops its collector rather than continuing without confirmed ownership. Collector status endpoints expose the coordination mode and state.

Migration 012 adds a monotonically increasing fencing generation. Every PostgreSQL write performed by the five scheduled collector groups checks the active owner token, generation, and lease expiry in the same transaction as the data write. The check takes a row-level shared lock on the lease record, so a concurrent takeover cannot advance the generation until that write transaction commits. A paused old worker that resumes after takeover is rejected at the database write boundary, even if its in-memory task has not yet processed the lost-lease signal.

SQLite/local development remains process-local and does not provide cross-process coordination or write fencing. A configured PostgreSQL `DATABASE_URL` is required for distributed leases. If `HISTORICAL_KLINE_DATABASE_URL` points to a separate database, leases still live in the shared primary `DATABASE_URL`; all replicas must share that primary coordination database. Manual API-triggered collection requests are not background lease owners; their writes continue through their endpoint-specific validation and upsert protections.

## Security

- Keep `PERSONAL_API_KEY` and `DATABASE_URL` only in Render's environment/secret settings.
- Do not commit `.env` or paste secrets into issues, pull requests, or chat.
- Keep auto-deploy disabled until CI is green and a manual deployment is explicitly approved.
- Do not merge PR #4 or deploy to production without the owner's explicit approval.
